# 교사용 수업 운영안 초안

상태: Phase 2 T01 초안. 실기기 검증과 교실 파일럿 전의 운영 제안이므로, 제안 시간·평가 비율을 실제 관찰 결과로 바꾸지 않는다. 웹 페이지의 `웹 ready`, `기기 verified`, `교실 파일럿 passed` 상태를 서로 섞어 쓰지 않는다.

## 1. 수업의 약속

이 수업의 목표는 장비가 “성공”하는 것이 아니라, 학생이 질문을 좁히고 관찰 근거를 남긴 뒤 보안 방어의 한계를 설명하는 것이다.

- **허가 범위:** 자신의 태그·공유기·휴대폰·리모컨처럼 소유하거나 사용 허가를 받은 대상만 관찰한다. 신용카드·교통카드·출입장치·타인의 기기는 사용하지 않는다.
- **실제와 사례 구분:** 학생이 직접 측정한 행은 `실제`, 교사가 제공한 예시는 `데모/사례`로 표시한다. 두 자료를 한 성공률이나 평균에 합치지 않는다.
- **중단 기준:** 장비가 과열되거나 배터리가 부족함, 주변 전파·개인정보에 영향이 우려됨, 허가 대상인지 모호함, 기록을 복구할 수 없음 중 하나면 즉시 멈춘다. 공책·사례 자료 경로로 이동한다.
- **증거 우선:** 화면에 없는 단위·패킷·성공을 추정해 채우지 않는다. 신호가 없으면 `미관찰`/`미측정`/`확인 안 됨`으로 남긴다.

## 2. 기본 A~E 수업안(각 50분 제안)

시간은 파일럿 전 제안치다. 장비 수보다 모둠이 많으면 한 모둠은 읽기·기록, 다른 모둠은 분석·보고서를 진행하고 15분마다 역할을 교대한다.

| 차시 | 흐름과 권장 시간 | 학생 산출물 | 교사 확인 질문 |
|---|---|---|---|
| 기본 A · 시작과 준비 | 생활 장면 8분 → `/start/` 준비 12분 → `/learn/device/` 메뉴·첫 읽기 20분 → 정리 10분 | 준비 체크, 메뉴 경로, 첫 태그 읽기 또는 실패 관찰 | “지금 확인한 것은 메뉴 표시인가, 실제 읽기인가?”, “실패를 0회 성공으로 적지 않은 이유는?” |
| 기본 B · 통신과 위협 | NFC/Wi-Fi 원리 15분 → 통신 단계 10분 → 위협 모델 15분 → 방어 설계 10분 | ATQA·UID·RSSI 등 용어 설명, 자산·위협·방어 가설 | “UID를 안다고 결제가 되는가?”, “관찰값 하나로 안전하다고 말할 수 있는가?” |
| 기본 C · 설계와 기록 | 변수·고정값 5분 → 예비 관찰 10분 → 반복 측정 25분 → 백업 10분 | 조건별 원자료, 결측 이유, 복구 가능한 CSV/서술 기록 | “무엇을 바꿨고 무엇을 고정했나?”, “같은 태그를 다시 읽은 기록인가?” |
| 기본 D · 분석과 방어 | 복구 5분 → 브라우저 표·그래프 15분 → 해석 10분 → 방어 비교 15분 → 정리 5분 | 사실/추정/한계가 분리된 표와 그래프, 방어 제안 | “그래프의 분모와 결측은 어디에 있나?”, “다른 원인 하나를 제시할 수 있나?” |
| 기본 E · 보고와 설명 | 근거 확인 5분 → 보고서 20분 → 동료 검토 10분 → 1분 자기설명 15분 | 질문→방법→근거→결과→방어→한계→후속 질문 보고서 | “실제로 한 일과 사례 자료를 분리해 말했나?”, “다음 실험은 무엇을 바꿀 것인가?” |

기본 경로는 `0 /learn/why/ → 1 /start/ → 2 /learn/device/ → 3 /learn/nfc/ → 4 /learn/network/ → 5 /learn/security/ → 6 /lab/nfc/`다. 학생이 중간에 실패하면 마지막으로 저장한 지점의 링크로 돌아가며, 처음부터 다시 하게 하지 않는다.

### 기본 A의 장비 회전

1. 모둠별로 리더·태그·전원·공책을 확인한다.
2. 한 명은 화면을 읽고, 한 명은 관찰 시각과 조건을 기록하며, 한 명은 안전·허가 범위를 확인한다.
3. 화면에 `Listening`이 오래 남거나 태그가 안 보이면 위치·방향을 한 번만 바꾼 뒤 `미관찰`로 기록한다. 연속해서 무작정 재시도하지 않는다.
4. 장비가 없거나 멈추면 NFC 장면의 제공 사례를 분석하고 “실제 확인이 필요한 항목”을 적는다. 사례 분석은 기기 검증으로 승격하지 않는다.

## 3. 선택 W · Wi-Fi RSSI 차시

`/lab/wifi-rssi/`의 수동 워크북을 사용한다. ESP32-DIV의 Wi-Fi 스캔 실행은 아직 기기 verified가 아니므로, 학생은 자신의 공유기·휴대폰·PC에서 허가된 값을 옮겨 적거나 교사가 준비한 사례 자료를 사용한다.

- 준비 10분: 같은 AP 별칭, 측정 도구, 방·거리·높이·방향·대기 시간을 정한다.
- 기록 20분: 방 3곳×5회는 제안치다. `관찰됨`, `미관찰`, `확인 안 됨`을 구분하고 RSSI가 없으면 0을 입력하지 않는다.
- 분석 15분: 브라우저의 표·그래프·결측 수로 방별 차이를 비교한다. 중앙값과 반복 수를 함께 적고, AP 수를 혼잡도나 속도로 환산하지 않는다.
- 방어·보고 5분: 공유기 위치·채널 확인·망 분리 같은 방어를 제안하되, 인터넷 속도 개선을 보장한다고 쓰지 않는다.

Wi-Fi 값을 얻을 수 없으면 사례 자료를 별도 `데모`로 입력하고, 실제 행과 섞이지 않게 한다. Python/Colab은 선택 활동이며 계정·설치 실패가 수업 완료를 막지 않는다.

## 4. 기록·복구·대체 활동

- 시작 전 한 모둠의 빈 기록을 만들고, 한 행을 입력한 뒤 새로 고침·내보내기·가져오기를 시범 보인다.
- 원본 CSV는 덮어쓰지 않고 `원본_날짜.csv`, `분석본_날짜.csv`처럼 새 파일로 저장한다. 공유 전 이름·주소·교실 위치·자유 서술의 재식별 단서를 가명 처리한다.
- 브라우저 저장이 사라지면 마지막으로 내보낸 CSV나 공책 기록을 복구한다. 복구하지 못한 행은 다시 측정한 것처럼 만들지 않고 결측으로 남긴다.
- 장비가 없거나 권한·전원 문제가 있으면 (1) 공책으로 절차·변수 설계, (2) 제공 사례의 표·그래프 분석, (3) 다음 확인 질문 작성 순서로 진행한다. 대체 경로 완료와 기기 경로 완료를 별도 표시한다.

## 5. 제안 평가 기준(초안)

아래 비율은 파일럿에서 검토할 제안치다. 태그 인식 성공률, GPS 고정 여부, RSSI 크기처럼 학생이 통제할 수 없는 결과를 점수로 주지 않는다.

| 영역 | 비율 | 충분한 근거 |
|---|---:|---|
| 질문·설계 | 20% | 생활 질문을 관찰 가능한 가설로 좁히고 변수·고정값·허가 범위를 적음 |
| 기록·복구 | 25% | 시각·조건·도구·관찰값·결측 이유를 남기고 CSV/공책을 다시 열 수 있음 |
| 분석·한계 | 25% | 원자료와 데모를 분리하고 사실·추정·대안 원인·표본 한계를 구분함 |
| 방어·생활 연결 | 20% | 보호할 자산, 위협, 방어 행동, 효과 확인 방법과 남은 한계를 설명함 |
| 자기 설명·출처 | 10% | 1분 안에 동기→방법→근거→결과→후속 질문을 말하고 출처를 표시함 |

교사는 각 항목에 `근거 있음 / 부분 근거 / 다시 확인`만 먼저 표시한다. 파일럿 전에는 학생 점수나 평균을 공개된 성공률처럼 제시하지 않는다.

## 6. 예상 질문과 답변

**“UID를 읽었는데 카드를 복제할 수 있나요?”**
아니다. UID는 식별자 일부를 보여 줄 뿐이며, 결제 인증·암호 키·단말기·발급사 검증을 포함하지 않는다. 이 수업에서는 카드 복제나 결제를 시도하지 않는다.

**“RSSI가 -50보다 -80이면 무조건 공격인가요?”**
아니다. RSSI는 도구·거리·벽·시각에 따라 달라지는 관찰값이다. 단위와 조건을 함께 적고, 공격 여부를 단정하지 않는다.

**“태그가 안 읽히면 실패인가요?”**
학습 실패가 아니다. 위치·방향·재질·전원 같은 대안 원인을 기록하고, 미관찰 상태에서 다음 확인 질문을 만들면 된다.

**“Colab을 못 쓰면 보고서를 못 쓰나요?”**
아니다. 브라우저 표·그래프가 필수 경로다. Colab은 선택 확장이고, 로그인·설치 실패는 대체 활동으로 처리한다.

**“사례 자료를 분석했는데 기기를 사용했다고 써도 되나요?”**
안 된다. 사례는 `데모/사례`, 직접 관찰은 `실제`로 명시한다. 기기 verified는 실제 기기와 펌웨어·메뉴 범위가 확인된 뒤에만 올린다.

## 7. 파일럿 전 체크와 미해결 사항

교사는 수업 전에 모둠 수, 실제 장비 수, 배터리·태그 상태, 허가 범위, 사용할 브라우저, 대체 사례 파일, CSV 저장 위치, 중단 연락 절차를 채운다. `docs/device-verification-log.md`와 `docs/classroom-pilot-log.md`에 날짜·확인자·실제 시도·실패·복구를 기록한 뒤에만 상태를 갱신한다.

현재는 웹 경로와 대체 활동을 설계한 상태이며, ESP32-DIV의 모든 메뉴 실행과 학생 학급 파일럿은 미검증이다. 따라서 이 문서는 **수업 준비 완료 선언이 아닌 운영 초안**이다. 파일럿에서 발견된 시간·메뉴·기록 복구 문제를 이 문서의 제안 시간과 FAQ에 반영한다.
